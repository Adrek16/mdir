# لوحة مدير ستور

لوحة إدارة مستقلة لمتجر **ستور**، صُممت للتشغيل المحلي ويمكن نشرها على Netlify Functions.
الواجهة بنفس هوية المتجر (Cairo، كريمي، حبر، نحاسي، عنابي)، والبيانات من نفس مشروع Supabase.
العملة **ريال يمني (ر.ي)**، والمدينة (صنعاء) يدخلها المدير من «معلومات المتجر».

> **الخطة الحاكمة لتطوير اللوحة:** [`docs/manager-screens-plan.md`](docs/manager-screens-plan.md)  
> **خطة شاشات العملاء:** `C:\Users\L\Desktop\stoor\docs\customer-screens-plan.md`

> **تحذير أمني:** التصميم الأصلي محلي (`127.0.0.1`) ويستخدم مفتاح `service_role`. نشر اللوحة على نطاق عام يجعل صفحة دخول المدير متاحة للجميع — راجع [النشر على Netlify](#النشر-على-netlify) قبل تفعيله.

## التشغيل

```bash
npm install
npm run dev     # http://127.0.0.1:4100
```

- `npm run dev` يعيد التشغيل تلقائياً عند تعديل الملفات.
- `npm start` تشغيل عادي بلا مراقبة.
- `npm run check` فحص صياغة نقطة الدخول.

### متغيرات البيئة

انسخ `.env.example` إلى `.env` واملأ:

| المتغير | الوصف |
|---|---|
| `HOST` | `127.0.0.1` — محلي فقط |
| `PORT` | `4100` |
| `SUPABASE_URL` | رابط مشروع المتجر |
| `SUPABASE_SERVICE_ROLE_KEY` | مفتاح الخادم — لا يظهر في المتصفح أبداً |
| `SESSION_SECRET` | مفتاح توقيع الجلسة (32 بايت عشوائية على الأقل) |
| `STORE_URL` | رابط المتجر المحلي (زر «المتجر») |
| `STORE_REVALIDATE_URL` | مسار تحديث كاش المتجر (اختياري) |
| `STORE_REVALIDATE_SECRET` | سر الـ webhook (اختياري) |

### النشر على Netlify

> **مهم:** Netlify Drop (سحب المجلد يدوياً) يستضيف ملفات ثابتة فقط ويعطي
> `Page not found` لأن المشروع بلا `index.html`. استخدم الربط مع GitHub:
> `Add new site → Import an existing project → GitHub → Adrek16/mdir`.

الإعداد جاهز في `netlify.toml`:

- `publish = "public"` — الأصول الثابتة (`/assets` و `/fonts`) تُخدَم من CDN مباشرة.
- كل طلب آخر يُوجَّه إلى `netlify/functions/api.mjs`، وهي تغلّف **نفس** تطبيق Express عبر `serverless-http`، فتبقى صفحات EJS وواجهات `/api/*` والجلسات الموقّعة كما هي.
- قوالب `views/**` تُنسخ داخل حزمة الدالة، ومسار الأصول يثبَّت على `/assets` تلقائياً في بيئة الدوال (بدل البصمة المتغيرة محلياً).

**متغيرات البيئة المطلوبة** — أضفها من `Site configuration → Environment variables` ولا تضعها في المستودع:

| المتغير | إلزامي | الوصف |
|---|---|---|
| `SUPABASE_URL` | نعم | رابط مشروع المتجر |
| `SUPABASE_SERVICE_ROLE_KEY` | نعم | مفتاح الخادم |
| `SESSION_SECRET` | نعم | سر توقيع الجلسة (32 بايت عشوائية على الأقل) |
| `STORE_URL` | لا | رابط المتجر (زر «المتجر») |
| `STORE_REVALIDATE_URL` / `STORE_REVALIDATE_SECRET` | لا | تحديث كاش المتجر |

بدون المتغيرات الثلاثة الأولى يعرض الموقع صفحة إعداد عربية (503) تذكر أسماء النواقص بدل انهيار الدالة؛ محلياً يظل `npm start` يتوقف برسالة واضحة. أمر البناء `npm ci` يثبّت الاعتماديات من `package-lock.json`؛ لا توجد خطوة تجميع للواجهة.

**تحذير أمني:** بنشر اللوحة على `*.netlify.app` تصبح صفحة `/login` في متناول الجميع. استخدم كلمة مرور قوية جداً، وفعّل حماية بكلمة مرور على مستوى الموقع أو قيّد الوصول، وراجع صلاحيات مفتاح `service_role`.

**فروق عن التشغيل المحلي:**

- حدّ محاولات الدخول مخزّن في الذاكرة، فلا يبقى بين استدعاءات الدالة.
- مهلة الدالة الافتراضية 10 ثوانٍ؛ طلبات Supabase البطيئة قد تتجاوزها.
- `npm start` يبقى كما هو عبر `server/index.js`، ولم يتغيّر سلوكه المحلي.

## بنية المشروع

```
مدير/
├─ server/
│  ├─ index.js              # Express + EJS + الملفات الثابتة + معالجة الأخطاء
│  ├─ env.js                # التحقق من متغيرات البيئة عند الإقلاع
│  ├─ session.js            # كوكي HttpOnly موقّع HMAC-SHA256
│  ├─ http.js               # ردود JSON موحّدة + أدوات مساعدة
│  ├─ supabase.js           # REST/Auth/Storage بلا SDK (service_role)
│  ├─ middleware/
│  │  └─ require-admin.js   # حارس الصفحات والـ API
│  ├─ routes/               # صفحة + نقاط API لكل قسم
│  └─ services/             # قواعد العمل والاستعلامات
├─ views/
│  ├─ partials/             # head / sidebar / topbar / foot / icon
│  └─ *.ejs                 # login / dashboard / orders / products / categories / settings
└─ public/
   ├─ fonts/                # Cairo محلي
   └─ assets/
      ├─ css/               # theme / layout / components + صفحات
      └─ js/
         ├─ shared.js       # الواجهة الواحدة للدوال المتكررة
         ├─ core/           # api / dom / format / ui / table / shell / domain
         └─ pages/          # سكربت كل صفحة
```

### قاعدة الدوال المتكررة

كل صفحة تستورد من ملف واحد:

```js
import { api, dom, fmt, ui, table } from "../shared.js";
```

`shared.js` يعيد تصدير وحدات صغيرة في `core/`، فلا تكرار بين الصفحات.
تسميات الحالات والدفع موجودة في `core/domain.js` فقط، ويستوردها الخادم أيضاً.

## الأمان

- المصادقة عبر **Supabase Auth**، والدور يُقرأ من `profiles.role = 'admin'`.
- الجلسة في كوكي `HttpOnly` + `SameSite=Lax` موقّع بـ HMAC، وتنتهي بعد 8 ساعات.
- لا `sessionStorage` ولا كلمة مرور ثابتة في الكود.
- المفتاح السري على الخادم فقط؛ RLS مفعّل بلا سياسات عامة.
- الإيصالات في bucket خاص وتُقرأ عبر بروكسي `/api/orders/:id/proof`.
- حد لمحاولات الدخول: 8 محاولات كل 15 دقيقة لكل عنوان.
- ترويسات أمان + CSP تمنع أي سكربت خارجي.

## ما هو مبني الآن

- تسجيل الدخول والخروج.
- القشرة (سايدبار + شريط علوي) وصفحة رئيسية بمؤشرات.
- الطلبات: بحث وفلاتر، تفاصيل، تغيير الحالة، مراجعة إيصال التحويل.
- المنتجات: قائمة وفلاتر وإحصاءات، إضافة/تعديل، تبديل الظهور، حذف نهائي، وألوان متعددة بمخزون لكل لون.
- **صور المنتجات**: صورة رئيسية + حتى 5 صور لكل لون (`POST /api/products/upload?scope=main|color`)، تُحفظ في `image_path` و`color_images` وتظهر في المتجر.
- التصنيفات: قائمة وأقسام رئيسية، إضافة/تعديل/حذف، وربط مباشر بمنتجات كل تصنيف.
- إعدادات الدفع: **الحساب البنكي + المحافظ المحلية** (قيد التطوير — انظر خطة اللوحة).
- **شاشة «معلومات المتجر»** (`/store-info`): كل النصوص الظاهرة للعميل (الاسم، الوصف، «نبذة عنا»، الترحيب، ساعات العمل، العنوان، رابط الخريطة، تواصل، حسابات اجتماعية) + **رفع شعار** (`POST /api/store-info/logo`، bucket `store-assets` عام 2MB، فحص magic bytes، ومعاينة + إزالة). كل حفظ يُعيد تحقق كاش المتجر.
- **تأكيد الطلب وخصم المخزون** (قيد التطوير): الطلب يصل «جديداً» بلا خصم، والمدير يتواصل واتساب/هاتف ثم يؤكد فيُخصم المخزون ذرّياً.
- **شاشة الطلبات الموسّعة** (قيد التطوير): فلاتر المخزون والتاريخ + لوحة تفاصيل + تأكيد/إلغاء/إعادة فتح من مكان واحد.
- **شاشة العملاء** (قيد التطوير): `/customers` لكل عميل مسجّل — طلباته وإنفاقه وملفه، مع ملاحظة داخلية.
- **شاشة التقارير** (قيد التطوير): `/reports` — مبيعات وأفضل المنتجات وطرق الدفع والعملاء والمخزون، مع تصدير CSV وطباعة.
- **مراجعة التقييمات** (قيد التطوير): شاشة `/reviews` لاعتماد/رفض تقييمات العملاء قبل ظهورها.

### قواعد الطلبات

- الطلب الجديد **لا يخصم مخزوناً**؛ الخصم عند «تأكيد الطلب» بعد التواصل مع العميل.
- إن نقصت الكمية عند التأكيد: لا خصم جزئي، ورسالة بأسماء القطع الناقصة.
- إلغاء الطلب المؤكد يحرّر المخزون عبر `release_order_stock` مرة واحدة.
- إعادة فتح طلب ملغي تعيده إلى «جديد» **بلا حجز مخزون**، والخصم يحدث عند التأكيد من جديد.
- اعتماد إيصال طلب جديد يؤكّده تلقائياً **ويخصم المخزون** عبر نفس دالة التأكيد.
- لا اعتماد/رفض إيصال بلا ملف مرفوع.
- بعد تغيير يؤثر على المتجر يُنادى `STORE_REVALIDATE_URL` إن كان مضبوطاً.

### قواعد المنتجات

- التحقق على الخادم مطابق لقواعد المتجر: السعر والمخزون غير سالبين.
- لا يوجد حقل رابط ولا حقل اسم إنجليزي في نموذج المنتج؛ `products.name_en` أُزيل من قاعدة البيانات نهائياً.
- رابط المنتج يُولَّد تلقائياً على الخادم: رابط تصنيفه + رقم متسلسل داخل التصنيف، مثل `perfumes-1-3`. لا يظهر في الواجهة ولا يُدخل يدوياً.
- عند نقل المنتج إلى تصنيف آخر يُحذف رابطه القديم ويُصرف له رقم جديد في التصنيف الجديد داخل دالة `stoor_move_product` الذرّية، ويُسجَّل القديم في `product_slug_history` ليحوّله المتجر تحويلاً دائماً (308).
- الأرقام تُصرف من عدّاد `slug_counters` ولا تُعاد بعد الحذف، فلا يتكرر رابط أبداً.
- كل إنشاء/تعديل/حذف يبلّغ المتجر بإعادة التحقق، فيظهر التغيير فور الحفظ.
- المنتج المخفي يختفي من المتجر فوراً، والحذف نهائي بلا سلة محذوفات.
- كل منتج مرتبط بتصنيف موجود؛ التصنيف يُتحقق منه على الخادم.
- الألوان تُحفظ داخل `products.colors` بالشكل `[{ name, hex, stock }]`، وبحد أقصى 20 لوناً بأسماء غير مكررة.
- حقل «المخزون الكلي» ديناميكي: يُحسب تلقائياً من مجموع مخزون الألوان، ويصبح للقراءة فقط عند وجود ألوان.
- `products.stock` يبقى المصدر الرسمي للمجموع، ودوال `reserve_stock` / `release_stock` تخصم وتعيد من اللون المطلوب والمجموع معاً.

### قواعد التصنيفات

- التصنيف مرتبط بقسم رئيسي واحد: «العطور» أو «الإكسسوارات» أو «الحقائب»، أو «بلا قسم».
- الجنس المتاح للمنتجات والتصنيفات: رجالي، نسائي، للجنسين، أطفال.
- رابط التصنيف يُولَّد تلقائياً على الخادم: القسم + رقم متسلسل داخل القسم — `perfumes-1`، `accessories-4`، و`general-1` للتصنيف بلا قسم. لا يظهر في الواجهة ولا يُدخل يدوياً.
- تغيير قسم التصنيف يعيد ترقيمه داخل القسم الجديد، ويغيّر بادئة روابط كل منتجاته مع الحفاظ على أرقامها، داخل دالة `stoor_move_category` الذرّية.
- كل تغيير في رابط تصنيف أو منتج يُسجَّل في `category_slug_history` أو `product_slug_history`، فيحوّل المتجر الروابط القديمة تحويلاً دائماً (308) بدل 404 — ولا تنكسر الروابط المفهرسة.
- سلسلة التغييرات تُدمج: `a → b` ثم `b → c` تجعل `a` و`b` يقفزان مباشرة إلى `c`.
- حقل «الاسم بالإنجليزي» للتصنيف (`categories.name_en`) باقٍ لأنه يظهر في ترويسة المتجر، ولم يبقَ له دور في توليد الرابط.
- لا يمكن حذف تصنيف يحتوي منتجات — تُنقل منتجاته أولاً (حماية على الخادم وقاعدة البيانات).
- كل تغيير في التصنيفات يبلّغ المتجر بإعادة التحقق.

### قواعد معلومات المتجر (`/store-info`)

- كل الحقول تُحفظ في `settings` مفتاح `store_info` ككائن واحد (لا أعمدة منفصلة).
- **الشعار**: يُرفع عبر `POST /api/store-info/logo` بجسم صورة خام (PNG/JPEG/WEBP/AVIF، ≤ 2MB)، يُفحص بـ magic bytes، ويُخزَّن في bucket `store-assets` العام بالمسار `logo/<uuid>.<ext>`. المسار يُولَّد على الخادم دائماً (لا يثق بالامتداد).
- `GET /api/store-info` يُرجع `{ info, logoUrl }` — `logoUrl` رابط عام مبني بـ `sbPublicUrl` (المعاينة تعتمد عليه بعد إعادة التحميل).
- إزالة الشعار: `DELETE /api/store-info/logo` تُفرغ `logoPath` ويبقى الشعار الافتراضي (رسم SVG) في المتجر.
- كل حفظ (`PUT /api/store-info`) يُنادي `STORE_REVALIDATE_URL` لإبطال كاش `store_info` في المتجر.

## الاختبارات

تعمل هذه السكربتات على نسخة حقيقية من قاعدة البيانات، تنشئ بيانات مؤقتة ثم تحذفها.
يجب أن يكون المدير على `4100` والمتجر على `3000`.

```bash
npm run test:acceptance   # الطلبات والإيصالات والإعدادات البنكية — 22 فحصاً
npm run test:catalog      # التصنيفات والألوان ومخزون كل لون — 27 فحصاً
npm run test:slugs        # الروابط التلقائية والنقل والتحويلات القديمة — 23 فحصاً
node scripts/verify-feature.mjs          # مسارات معلومات المتجر + رفع الشعار — 23 فحصاً
node scripts/verify-product-images.mjs   # استمرارية image_path/color_images — 8 فحوص
```

> إن انقطعت الشبكة أثناء الاختبار يعيد السكربت المحاولة تلقائياً، وينظّف بياناته في كل الأحوال.

### قواعد الدفع والمحافظ (قيد التطوير)

- شاشة `/settings` تدير **قائمة طرق دفع**: بنوك + محافظ محلية (جوالي، جيب، حاسب، فلوسك، ون كاش، وأي اسم آخر).
- كل طريقة: نوع، اسم، اسم صاحب الحساب، رقم الحساب/المحفظة، ملاحظة، تفعيل، ترتيب.
- تُحفظ في `settings` بمفتاح `payment_methods`، مع تحويل تلقائي لبيانات `bank_transfer` القديمة.
- الطرق المعطّلة لا تظهر في المتجر.

### قواعد مزايا المنتج (قيد التطوير)

- قسم «مزايا المنتج (اختياري)» يظهر فقط لتصنيفات **الإكسسوارات**.
- خيارات جاهزة: منتج أصلي، استبدال ١٤ يوم، ضد الماء، لون لا يتغير + نص حر.
- تُحفظ في `products.features`، ولا تؤثر على منتجات العطور.
