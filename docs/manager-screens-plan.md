## 2. قسم «الدفع والمحافظ» — بدل شاشة الحساب البنكي

### 2.1 الوضع الحالي

- شاشة واحدة `/settings` لبيانات **حساب بنكي واحد**.
- المفتاح `bank_transfer` في جدول `settings`.
- الحقول: اسم البنك، اسم صاحب الحساب، الآيبان، ملاحظة.

### 2.2 المطلوب

شاشة تدير **قائمة طرق دفع**:

```
طرق الدفع
├─ بنوك
│  ├─ بنك التضامن — 1234567890
│  └─ بنك الكريمي — 9876543210
└─ محافظ
   ├─ جوالي — 77xxxxxxx
   ├─ جيب — 71xxxxxxx
   ├─ حاسب — 73xxxxxxx
   ├─ فلوسك — 70xxxxxxx
   └─ ون كاش — 78xxxxxxx
```

المدير يستطيع: **إضافة · تعديل · حذف · ترتيب · تعطيل/تفعيل** أي طريقة، ويكتب اسم أي محفظة أخرى.

### 2.3 نموذج البيانات

مفتاح جديد في `settings`: `payment_methods`

```json
[
  {
    "id": "pm_xxx",
    "type": "bank",
    "name": "بنك التضامن",
    "accountName": "مؤسسة ستور",
    "accountNumber": "1234567890",
    "note": "حوّل ثم ارفع الإيصال",
    "active": true,
    "sort": 1
  },
  {
    "id": "pm_yyy",
    "type": "wallet",
    "name": "جوالي",
    "accountName": "ستور",
    "accountNumber": "770000000",
    "note": "",
    "active": true,
    "sort": 2
  }
]
```

### 2.4 القواعد

1. `type`: `bank` أو `wallet` فقط.
2. الاسم مطلوب (حتى ٨٠ حرفاً).
3. رقم الحساب/المحفظة مطلوب (حتى ٦٠ حرفاً، أرقام ورموز آمنة).
4. اسم صاحب الحساب اختياري للمحافظ، مطلوب للبنك.
5. حد أقصى ١٠ طرق، وطريقة مفعّلة واحدة على الأقل.
6. لا HTML — تنظيف كامل على الخادم.
7. كل حفظ يُنادي `STORE_REVALIDATE_URL`.
8. **توافق خلفي:** عند أول قراءة، إن لم يوجد `payment_methods`، تُحوَّل بيانات `bank_transfer` القديمة إلى عنصر بنكي واحد.

### 2.5 الملفات

| الملف | التغيير |
|---|---|
| `server/services/settings.service.js` | استبدال `getBankTransfer/saveBankTransfer` بـ `getPaymentMethods/savePaymentMethods` + تحويل القديم |
| `server/routes/settings.routes.js` | `GET/PUT /api/settings/payment-methods` |
| `views/settings.ejs` | قائمة ديناميكية + نموذج إضافة |
| `public/assets/js/pages/settings.js` | إضافة/تعديل/حذف/ترتيب/تفعيل |
| `public/assets/css/pages/settings.css` | أنماط القائمة |
| `views/partials/sidebar.ejs` | تسمية «الدفع والمحافظ» |

### 2.6 أثرها على المتجر

- `GET /api/checkout/config` يعيد `methods` بدل `transfer` واحد.
- صفحة الإتمام تعرض الطرق المفعّلة فقط.
- اختيار طريقة يعرض بياناتها + رفع الإيصال.
- لا تظهر أي طريقة غير مفعّلة.
- الطلب يخزّن `payment_method_id`، ويُوسَّع قيد `orders.payment` ليصبح `cod | transfer | wallet` (تُحذف `card` الميتة).

## 4. تأكيد الطلب وخصم المخزون

### 4.1 الوضع الحالي

- الطلب يُخصم مخزونه **فور الإرسال** من المتجر (`reserve_stock`).
- اللوحة فيها `release_order_stock` لإرجاع المخزون عند الإلغاء، و`reserve_order_stock` كانت تُستخدم عند إعادة الفتح — ستتوقف عن الحجز نهائياً.
- الحالات: `new | confirmed | completed | cancelled`.

### 4.2 التدفّق المطلوب

```
طلب جديد (new)
   │
   ├─ المدير يتواصل واتساب/هاتف
   │
   ├─ «تأكيد الطلب وخصم المخزون»
   │     ├─ نجاح → confirmed + stock_state=reserved
   │     └─ نقص → رسالة بالقطع الناقصة، يبقى new
   │
   └─ إلغاء → cancelled (لا مخزون مخصوم)
```

### 4.3 التغييرات

| # | التغيير | الملف |
|---|---|---|
| 1 | عمود `orders.stock_state` (`none/reserved/released`) | `stoor/supabase/schema.sql` |
| 2 | دالة `confirm_order_stock(p_order_id)` ذرّية | نفس الملف |
| 3 | إزالة الحجز من `POST /api/orders` في المتجر | `stoor/src/app/api/orders/route.ts` |
| 4 | `POST /api/orders/:id/confirm` | `server/routes/orders.routes.js` |
| 5 | `confirmOrder(id)` في الخدمة + معالجة `OUT_OF_STOCK` | `server/services/orders.service.js` |
| 6 | زر «تأكيد وخصم المخزون» + شارة حالة المخزون | `views/orders.ejs` · `pages/orders.js` |
| 7 | أزرار واتساب/هاتف برسالة جاهزة | `views/orders.ejs` |
| 8 | إعادة فتح الطلب: `new` بلا حجز (إزالة `reserve_order_stock` من مسار إعادة الفتح) | `server/services/orders.service.js` |

### 4.4 قواعد

- لا خصم قبل التأكيد.
- التأكيد ذرّي: يفحص كل الألوان والكميات أولاً.
- إن نقص أي منتج: لا خصم جزئي، ورسالة واضحة بأسماء المنتجات.
- الإلغاء بعد التأكيد يعيد المخزون مرة واحدة فقط (`stock_released` يمنع التكرار).
- الطلب الملغى لا يمكن تأكيده إلا بعد إعادة فتحه، **وإعادة الفتح لا تحجز مخزوناً** — تعيده إلى `new` فقط، والخصم يحدث عند التأكيد من جديد.
- زر «تأكيد» لا يظهر لطلب ملغى أو مؤكد.

### 4.5 أزرار التواصل

رسالة واتساب جاهزة:

```
مرحباً {اسم العميل}، بخصوص طلبك {رقم الطلب} من ستور:
{أسماء المنتجات والكميات}
الإجمالي: {المبلغ} ر.ي
نرجو تأكيد الطلب وتحديد موعد الاستلام من المتجر.
```

- زر واتساب يفتح `wa.me/{967…}`.
- زر هاتف `tel:`.
- **إصلاح مطلوب:** `normalizePhone` في `core/format.js` يضيف `966` — يجب أن يضيف `967`.

### 4.6 شاشة الطلبات (`/orders`)

الشاشة موجودة، وتُوسَّع لتكون مركز العمل اليومي:

**أ) الفلاتر**

| الفلتر | القيم |
|---|---|
| بحث | رقم الطلب · اسم العميل · الجوال |
| حالة الطلب | الكل · جديد · مؤكد · مكتمل · ملغى |
| طريقة الدفع | الكل · عند الاستلام · تحويل بنكي · محفظة |
| حالة الدفع | الكل · غير مدفوع · بانتظار المراجعة · مدفوع · مسترد |
| حالة المخزون | الكل · لم يُخصم · مخصوم · أُعيد |
| التاريخ | من — إلى |

**ب) الجدول**

| العمود | المحتوى |
|---|---|
| الطلب | الرقم + التاريخ |
| العميل | الاسم + الجوال |
| القطع | عدد الأصناف والوحدات |
| الإجمالي | بالريال اليمني |
| الدفع | الطريقة + حالة الدفع |
| المخزون | شارة «لم يُخصم / مخصوم / أُعيد» |
| الحالة | شارة ملوّنة |
| إجراء | تفاصيل · واتساب · هاتف |

- ترقيم صفحات ٢٥/٥٠، وترتيب افتراضي الأحدث أولاً.
- حالة فراغ واضحة، وزر تحديث.

**ج) لوحة تفاصيل الطلب**

```
بيانات العميل (اسم، جوال، بريد الحساب)
القطع: المنتج · اللون · الخيار · الكمية · سعر الوحدة · المجموع
الإجمالي (بلا شحن ولا ضريبة)
طريقة الدفع + الإيصال (معاينة/اعتماد/رفض)
الخط الزمني: أُنشئ → عُدّل → أُكّد → اكتمل/أُلغي
ملاحظة داخلية للمدير
أزرار: تأكيد وخصم المخزون · إلغاء · إعادة فتح · واتساب · هاتف
```

- «تأكيد وخصم المخزون» لا يظهر إلا لطلب `new`.
- «إلغاء» متاح لـ `new` و`confirmed` (مع تحرير المخزون إن كان مخصوماً).
- «إعادة فتح» لطلب ملغى فقط، ويعيده إلى `new` **بلا حجز مخزون**.
- اعتماد الإيصال يؤكد الطلب **ويخصم المخزون** عبر نفس دالة التأكيد؛ وإن نقص المخزون يبقى `new` مع رسالة واضحة.

**د) الملفات:** `views/orders.ejs` · `public/assets/js/pages/orders.js` · `public/assets/css/pages/orders.css` · `server/routes/orders.routes.js` · `server/services/orders.service.js`.

## 5. شاشة العملاء (`/customers`) — جديدة

### 5.1 الهدف

كل عميل مسجّل له ملف واحد يجمع بياناته وطلباته وإنفاقه، بلا الحاجة للبحث في الطلبات.

### 5.2 قائمة العملاء

**المصدر:** `profiles` (حيث `role = 'customer'`) + تجميع من `orders` عبر `customer_id`.

| العمود | المحتوى |
|---|---|
| العميل | الاسم + البريد |
| الجوال | `profiles.phone` إن وُجد، وإلا آخر جوال في الطلبات |
| الطلبات | العدد الإجمالي |
| الإنفاق | مجموع الطلبات المؤكدة/المكتملة بالريال اليمني |
| آخر طلب | التاريخ |
| انضم | تاريخ إنشاء الحساب |
| إجراء | عرض الملف · واتساب |

**الفلاتر:** بحث (اسم/بريد/جوال) · لديه طلبات / بلا طلبات · عملاء متكررون (طلبين فأكثر) · تاريخ الانضمام.

**مؤشرات أعلى الصفحة:** إجمالي العملاء · عملاء هذا الشهر · مشترون · نسبة التكرار.

### 5.3 ملف العميل (`/customers/:id`)

- بيانات الحساب: الاسم، البريد، تاريخ الانضمام، مزوّد الدخول.
- إحصاءات: عدد الطلبات، إجمالي الإنفاق، متوسط قيمة الطلب، أول/آخر طلب.
- جدول طلباته (بنفس أعمدة شاشة الطلبات) مع رابط لكل طلب.
- أزرار واتساب/هاتف.
- **ملاحظة داخلية** يكتبها المدير (`profiles.admin_note`) — لا تظهر للعميل.
- لا إدارة لكلمة المرور من اللوحة.

### 5.4 البيانات والترحيل

- `orders.customer_id uuid references auth.users(id) on delete set null` + فهرس.
- `profiles.admin_note text` (اختياري).
- `profiles.phone text` (اختياري) — يُستخدم في شاشة العملاء بدل الاعتماد على آخر طلب.
- **ترحيل الطلبات القديمة:** ربطها بالحساب عبر تطابق `customer_phone` مع آخر جوال معروف، وما لا يُطابق يبقى `customer_id = null` ويظهر بوسم «طلب قديم».
- لا حذف لحساب العميل من اللوحة (خارج النطاق) — يمكن تعطيله لاحقاً.

### 5.5 الملفات

| الملف | التغيير |
|---|---|
| `server/routes/customers.routes.js` | جديد: `/customers` و`/customers/:id` و`GET /api/customers` |
| `server/services/customers.service.js` | جديد: تجميع العملاء والطلبات |
| `views/customers.ejs` · `views/customer.ejs` | جديد |

## 6. شاشة التقارير (`/reports`) — جديدة

### 6.1 الهدف

أرقام حقيقية من الطلبات والتقييمات، لا إدخال يدوي. تُقرأ من الطلبات المؤكدة والمكتملة فقط لقيمة المبيعات.

### 6.2 النطاق الزمني

- اليوم · آخر ٧ أيام · آخر ٣٠ يوماً · هذا الشهر · الشهر الماضي · نطاق مخصص.
- التوقيت: **Asia/Aden (UTC+3)**.

### 6.3 المؤشرات الرئيسية

| المؤشر | المعادلة |
|---|---|
| الإيراد | مجموع `total` للطلبات `confirmed` + `completed` |
| عدد الطلبات | كل الحالات، مع تفصيل |
| متوسط قيمة الطلب | الإيراد ÷ عدد الطلبات المؤكدة/المكتملة |
| الوحدات المباعة | مجموع كميات `items` |
| نسبة الإلغاء | الملغاة ÷ كل الطلبات |
| عملاء جدد | حسابات أُنشئت داخل النطاق |
| عملاء متكررون | طلبان مؤكدان فأكثر |
| الأكثر مبيعاً | من `sales_count` الحقيقي |
| الأعلى تقييماً | من `rating` الحقيقي |

### 6.4 التقارير

1. **المبيعات عبر الزمن** — رسم أعمدة/خط يومي أو شهري (SVG بلا مكتبات خارجية).
2. **أفضل ١٠ منتجات** — بالوحدات وبالإيراد.
3. **أفضل التصنيفات** — وحدات وإيراد.
4. **طرق الدفع** — عدد الطلبات والمبالغ لكل طريقة (عند الاستلام/بنك/محافظ).
5. **العملاء** — أفضل ١٠ عملاء بالإنفاق، ونسبة الجدد مقابل المتكررين.
6. **المخزون** — منتجات نفدت، ومنتجات أقل من حد أدنى.
7. **الإلغاءات** — عددها وأسبابها إن سُجّلت ملاحظات.

### 6.5 التصدير والطباعة

- زر **CSV** لكل جدول (UTF-8 مع BOM حتى تظهر العربية في Excel).
- زر **طباعة** بتنسيق نظيف (بلا سايدبار).
- اسم الملف يتضمن النطاق الزمني.

### 6.6 القواعد

- لا أرقام يدوية ولا تقديرات — كلها من `orders` و`products` و`profiles`.
- الطلبات `new` و`cancelled` لا تُحتسب في الإيراد.
- الإلغاء بعد التأكيد يُنقص المبيعات مرة واحدة (نفس trigger الترتيب).
- التقرير للقراءة فقط — لا تعديل من داخله.

## 7. تقييمات العملاء — شاشة مراجعة جديدة

### 7.1 المطلوب

شاشة `/reviews` تعرض:

```
التقييمات
├─ بانتظار المراجعة (عدّاد)
├─ معتمدة
├─ مرفوضة
└─ بحث بالمنتج/العميل
```

لكل تقييم: المنتج، العميل، النجوم، النص، تاريخ الطلب، أزرار:

- **اعتماد** → يظهر في المتجر ويُحدَّث متوسط المنتج.
- **رفض** → يبقى محفوظاً ولا يظهر.
- **رد المدير** (اختياري) → يظهر تحت التعليق.
- **حذف نهائي**.

### 7.3 القواعد

- لا يظهر تقييم قبل الاعتماد.
- الاعتماد يُحدّث `products.rating` و`products.reviews` (كاش معروض، والقيم محسوبة من التقييمات المعتمدة فقط).
- الرفض لا يحذف التقييم — يمكن إعادة النظر.
- حذف المنتج يحذف تقييماته (`on delete cascade`).
- كل تغيير يُنادي `STORE_REVALIDATE_URL`.

## 8. الترتيب والمبيعات — بيانات محسوبة لا يدوية

### 8.1 المبدأ

المدير **لا يحدّد** «الأكثر مبيعاً» ولا «الأعلى تقييماً» بنفسه:

| الترتيب | مصدره الحقيقي | ما يفعله المدير |
|---|---|---|
| الأكثر مبيعاً | الطلبات المؤكدة/المكتملة | لا شيء — يُحسب تلقائياً |
| الأعلى تقييماً | تقييمات العملاء المعتمدة | يعتمد/يرفض التقييم فقط |
| الأكثر رواجاً | مزيج مبيعات + تقييم + حداثة | لا شيء |

### 8.2 ما يتغيّر في اللوحة

1. **نموذج المنتج:**
   - حذف خيار «الأكثر مبيعاً» من قائمة الشارات اليدوية.
   - تبقى الشارات التحريرية: «جديد»، «خصم»، «إصدار محدود».
   - لا توجد حقول لإدخال `rating` أو `reviews` (غير موجودة أصلاً — تُترك محسوبة).
2. **قائمة المنتجات:**
   - أعمدة جديدة للقراءة فقط: **المبيعات**، **متوسط التقييم**، **عدد التقييمات**.
   - لا يمكن تعديلها من الجدول.
3. **لوحة المعلومات:**
   - «الأكثر مبيعاً» تُعرض من `sales_count` الحقيقي، لا من `sort_order`.
   - «أعلى تقييماً» من `rating` الحقيقي.
4. **الطلبات:**
   - تأكيد الطلب يزيد `sales_count`.
   - إلغاء طلب مؤكد يُنقصه مرة واحدة.

### 8.3 الحساب

- `products.rating` = متوسط مرجّح (Bayesian, m=5) من التقييمات **المعتمدة** فقط (عمود موجود يُعاد استخدامه).
- `products.reviews` = عدد التقييمات المعتمدة (عمود موجود يُعاد استخدامه).
- `sales_count` = مجموع وحدات `orders.items` للطلبات `confirmed` و`completed` (عمود جديد).
- `popularity_score` = 0.6 × مبيعات + 0.3 × تقييم + 0.1 × حداثة (عمود جديد).
- كلها تُحدَّث بـ triggers، لا بحساب وقت العرض.

### 8.4 الملفات

| الملف | التغيير |
|---|---|
| `stoor/supabase/schema.sql` | أعمدة + triggers |
| `server/services/products.service.js` | إرجاع الحقول المحسوبة للقراءة فقط |
| `views/products.ejs` | أعمدة المبيعات/التقييم + إزالة شارة «الأكثر مبيعاً» |
| `public/assets/js/pages/products.js` | عرض للقراءة فقط |
| `server/services/dashboard.service.js` | أفضل المبيعات من البيانات الحقيقية |
| `views/dashboard.ejs` | بطاقة «الأكثر مبيعاً» |
| `public/assets/js/core/domain.js` | تحديث خيارات الشارات |

### 8.5 معايير القبول

- [ ] لا يستطيع المدير اختيار شارة «الأكثر مبيعاً».
- [ ] لا يستطيع المدير إدخال رقم مبيعات أو تقييم.
- [ ] تأكيد طلب يرفع المبيعات ويظهر في اللوحة والمتجر.
- [ ] اعتماد تقييم يرفع المتوسط ويغيّر الترتيب.
- [ ] إلغاء طلب مؤكد يُنقص المبيعات مرة واحدة.
